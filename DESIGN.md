# rbxdserver — что это и зачем

Простым языком, без технических деталей (они — в `AGENTS.md` и `ISSUES.md` рядом).
Этот файл — чтобы помнить, **зачем** демон вообще существует и куда его вести.

## Что это такое

Маленький демон на Go, который крутится 24/7 как NixOS-сервис (`services.boblox`,
см. `module.nix`). Сам по себе он **не запускает Roblox** — он следит за плейсами и
делегирует настоящую работу `rbxd` (Python-движку), запуская его как дочерний процесс.

## Зачем он нужен — четыре работы

```
┌──────────────────────────────────────────────────────────────────────┐
│  rbxdserver (Go, 24/7, копейки ресурсов)                              │
│                                                                       │
│  0. CDN-ВЕБ (постоянный, с ним и живёт демон)                          │
│     rbxd `webserver` без конфига (v347, без Wine) на --cdn-port:      │
│     общие ассеты data/Assets, скины, thumbnails. Клиент может         │
│     смотреть/менять скины, даже когда ни один плейс не запущен.       │
│                                                                       │
│  1. КАТАЛОГ ПЛЕЙСОВ (аналог roblox.com)                               │
│     сканит <places-dir>/*/GameConfig.toml → отдаёт список: название,  │
│     версия, описание, иконка. Клиент рисует карточки.                 │
│                                                                       │
│  2. ЗАПУСК ПЛЕЙСА ПО КНОПКЕ                                            │
│     POST /start?place=<slug> → поднял сессию (веб-процесс + RCC-      │
│     процесс) → дождался RFD_RCC_READY → отдал порты клиенту.          │
│                                                                       │
│  3. СЛЕЖЕНИЕ: RCC НЕ ДОЛЖЕН ЖРАТЬ ЖЕЛЕЗО ВПУСТУЮ                        │
│     кто в игре — говорит сам rbxd (presence: заполняется на             │
│     join-турникете, чистится Lua-хуком PlayerRemoving внутри RCC).     │
│     Никого --empty-timeout (5 мин) → RCC убивается сразу; веб сессии   │
│     живёт ещё 4 мин (кулдаун) — если тот же плейс запустили снова,     │
│     он переиспользуется и старт почти мгновенный. Зашёл хотя бы один   │
│     — таймер снят, даже в последние секунды.                           │
│                                                                       │
│  4. ВЕБ-ПАНЕЛЬ (GET /) — тестовая                                     │
│     статус, кто онлайн, кнопки запуска из /places и join-команды —    │
│     чтобы проверить всё без rbxdclient. Это инструмент отладки,       │
│     а не конкурент клиенту.                                           │
└──────────────────────────────────────────────────────────────────────┘
```

**Архитектура «веб 24/7 + RCC по требованию» из `../rbxd/INTEGRATION.md` §10 —
реализована (2026-09)**, в виде: постоянный CDN-веб + сессия из двух
независимых процессов rbxd (веб сессии и RCC).

## Почему только один запущенный плейс?

Это **намеренно**, а не потому что «rbxd так может только один»:

- Ты играешь один, и «2 разных или одинаковых плейсов одновременно» тебе не нужно.
  Один плейс = один RCC = минимум ресурсов. Это **фича**, не ограничение.
- Это совпадает с ограничением самого Roblox: один живой `RCCService.exe` на *версию*
  на дерево rbxd — общие файлы `GameServer.json` / `RCCFlagOverride.json` в
  `Roblox/<version>/Server/`. (v347 + v463 могли бы ужиться — разные папки, но тебе это
  не нужно.)
- Сам rbxd при этом умеет поднять N плейсов одним процессом (несколько `--config`).
  Так что «один плейс» — потолок именно rbxdserver, и его можно ослабить, если
  когда-то захочется играть с кем-то в разные плейсы.

## Что было плохого в старом коде — и что стало

Старые беды (гонки супервизора, path-traversal, fail-open auth, WS-«чёрная дыра»,
блокирующий старт, deprecated `--state-dir`) — закрыты реврайтом 2026-09, детали
в `AGENTS.md` (раздел «Что сделано») и `API.md`. Остались компромиссы, они
там же перечислены: presence по username, TOCTOU UDP-порта RCC, нет тестов.

## Скины — мечта, которая УЖЕ наполовину работает

Ты собираешь скины (`skinpacksidk` — список ссылок roblox.com/catalog/…, `skins/*.json` —
готовые аватары). Хорошие новости: **серверная часть уже готова и живёт в rbxd**:

- `rbxd/Source/web_server/endpoints/avatar.py` → `get_avatar()` читает скин из файла
  `skins/<user_code>.json`. Это форковая фича, которая подменяет обычный конфиг-хук.
- При первом заходе `skins/default.json` автоматически копируется в
  `skins/<твой_ник>.json`. То есть у каждого игрока — свой файл аватара.
- Формат файла — ровно то, что лежит у тебя в `skins/`:
  `{"type": "R6"|"R15", "items": [id ассетов], "scales": {…}, "colors": {…}}`.
- Фаил читается **при каждом запросе** (без кэша) — поменял JSON, и в игре аватар
  сменился без рестарта сервера.
- «3D» — это ассеты по ID из каталога Roblox; их сам движок тянет через AssetCache.
  Тебе нужно только правильно собрать набор ID.

Чего не хватает (wishlist):

1. **Конвертер `skinpacksidk` → `skins/*.json`**: из ссылки `roblox.com/catalog/<id>/…`
   доставать `<id>` и раскладывать по частям (torso, left_arm, …) — сейчас это делаешь
   руками.
2. **UI в rbxdclient**: выбрать скин из коллекции, посмотреть превью, положить в
   `skins/<ник>.json`. Превью 3D — на будущее; для начала хватит превью-картинки
   (клиент уже умеет `avatar_path` — простая PNG-картинка в окне входа).

Что уже появилось (2026-09):

- **Сетевой API скинов в rbxdserver**: `GET /skins`, `GET /PUT /skins/<name>.json`
  — клиент с ноутбука может смотреть коллекцию и сохранять скины на сервер, без
  ssh и файлопашки (детали — `API.md`). rbxd при этом не тронут: его аватар-эндпойнт
  как читал `skins/<user_code>.json` на каждый запрос, так и читает — запись через
  API подхватывается вживую.
- **CDN-веб**: скины и превью (`avatar-thumbnail/image` и пр.) доступны с
  фиксированного порта `--cdn-port` постоянно, даже когда плейс не запущен.

Один источник правды для скинов по-прежнему файловая система (`<rfd>/data/skins/`);
идея отдельного каталога в `--data-dir` осталась нереализованной — API ходит прямо
в каталог rbxd через `--skins-dir`.

## Присутствие игроков — почему сейчас «колхоз» и как починить

Сейчас rbxdserver узнаёт «кто в игре» через WS на `/session`: клиент держит сокет открытым,
пока играет; закрыл — через 15 c плейс стопится. Проблемы: ключ сессии — ник (два «Player»
сольются в одного), сокет — «чёрная дыра» (нет ping/deadline), а если клиент упал на старте,
сервер вообще не узнает об игроке.

**А rbxd-то знает лучше.** Каждый игрок неминуемо проходит через вебсервер rbxd —
`init_player()` в `web_server/endpoints/join_data.py` вызывается из `negotiate.ashx` /
`join.ashx`. Это единая «турникетная» точка, где уже известны `user_code`, `username`,
`iden_num`.

**Проверено на реальном логе** (см. `../rbxd/INTEGRATION.md` §11): последовательность
`negotiate → join.ashx → data-transfer` видна чётко, а вот **при выходе игрока лог
обрывается на обычном запросе — вебсервер вообще ничего не замечает**. RCC в stdout тоже
молчит.

Зато выяснилось кое-что получше. В rbxd генерируется Lua-скрипт
(`routines/rcc/startup_scripts.py`), который крутится **внутри самого RCC** — а RCC прощание
с игроком видит наверняка, это игровой движок. Он уже реагирует на `PlayerAdded` (шлёт
`GET /rfd/is-player-allowed`), а добавить `PlayerRemoving` — пять строк Lua:

```lua
game.Players.PlayerRemoving:connect(function(Player)
    HttpRbxApiService:PostAsync("rfd/player-left?userId=" .. Player.UserId, "")
end)
```

**«Следить изнутри, а не снаружи»** — единственный авторитетный источник: не «процесс
умер» и не «тишина 30 c», а событие от движка. И join, и leave теперь приходят из одного
места. Остальные сигналы (обёртка player, pull presence, трекер тишины) — фолбэки на случай
смерти самого RCC.

**Можно протестировать уже сейчас**, не трогая rbxd: в `~/.boblox/Places/<slug>/GameConfig.toml`
есть `startup_script` — любой Lua оттуда выполняется при старте сервера.

Подробно — `../rbxd/INTEGRATION.md` §11 (канал 0 + пересмотренная сводка).

## Каталог ассетов — зачем серверу знать типы

Сейчас AssetCache плоский: файлы без расширений, без имён, без типов. Собрать скин или
найти нужный звук можно только вслепую, по ID. А тип узнать **бесплатно** — публичный
эндпойнт без куки:

```
GET https://economy.roblox.com/v2/assets/<id>/details → {"AssetTypeId": 12, "Name": "…"}
```

Идея: один раз проиндексировать кэш в sqlite `(id, type, name, creator)`, потом
дописывать только свежескачанные. rbxd отдаёт `GET /rfd/asset-catalog?type=Pants&q=…`,
rbxdserver проксирует, rbxdclient рисует «надеть скин» и мини-Toolbox.

**Причём тут rbxdserver.** Сейчас AssetCache — свой на каждый плейс, одни и те же
ассеты качаются заново. А сервер — идеальное место для **общего** кэша и общего индекса:
он один, живёт 24/7, и все плейсы через него проходят. Тогда скин, собранный в одном
плейсе, виден в любом другом.

Подробно — `../rbxd/INTEGRATION.md` §12.

## Toolbox в Studio — почему сниффать процессы не нужно

Studio запускается (`python3 _main.py studio --backend proton`), Toolbox-плагин грузится
(FLog: `Plugin load time 'builtin_Toolbox.rbxm'`). Но его API никто не обслуживает —
нужные эндпойнты отдают 404.

**Главный трюк**: BaseURL переведён на локальный вебсервер, поэтому **любой** запрос
Studio прилетает в твой собственный rbxd. Маршрутизатор пишет в лог каждый путь, а
нереализованные → 404. То есть TODO-список для Toolbox собирается вычитанием логов, а не
mitmproxy или трассировкой процессов:

```
запросы из лога вебсервера  −  то, что есть в @server_path  =  чего не хватает
```

Из реального лога уже всплыли кандидаты: `/Analytics/Measurement.ashx`,
`/Persistence/GetBlobUrl.ashx`, `/userblock/getblockedusers`,
`/users/<id>/canmanage/<place>`. Catalog-API Toolbox в логах ещё не появлялся —
нужно открыть Toolbox в Studio и походить по нему.

Подробно — `../rbxd/INTEGRATION.md` §13.
